How to keep a MacBook awake with the lid closed — every method, honestly compared

Updated August 2026 · no affiliate links, and we make one of the tools below (disclosed)

Close a MacBook's lid and macOS puts it to sleep unless power, an external display and a keyboard are attached. Every guide covers that part. Almost none cover the second half: an awake Mac with no display still can't render its GUI — screen capture goes black, remote desktop shows nothing, windows drift into a phantom layout. Here's what each fix actually solves.

The two problems hiding in one lid

Sleep. Lid closes → machine sleeps. Builds stop, downloads pause, SSH drops, coding agents die mid-task.

The display. Beat sleep, and with no monitor attached macOS still tears down the display coordinate space. The machine hums along headless — but GUI apps have nothing to draw on. Awake isn't the same as usable. If you only need SSH or background jobs, solving sleep is enough. If you need to see or control anything graphical, you need both halves.

Method 1: caffeinate (built in, free)

caffeinate -i long_running_command

Prevents idle sleep while a command runs. Does not survive a lid close — clamshell sleep overrides it. Good for "don't sleep during this build with the lid open," and that's all.

Method 2: pmset disablesleep (built in, free, root)

sudo pmset -a disablesleep 1   # lid-close no longer sleeps
sudo pmset -a disablesleep 0   # put things back

The real override: the Mac stays awake with the lid shut, no hardware needed. Two catches: it needs root and is easy to forget to undo (battery drain in a bag), and it solves only the sleep half — headless GUI stays unreachable.

Method 3: keep-awake utilities (Amphetamine, KeepingYouAwake)

Friendly menu-bar wrappers around the same idea — sessions, timers, triggers. Note that Amphetamine by itself deliberately does not allow closed-lid-without-display operation; its companion "Enhancer" adds that. Same limitation as pmset: sleep only, no display.

Method 4: the dummy HDMI plug (~$8, hardware)

A little adapter that impersonates a monitor at the EDID level. macOS believes a display is attached, so clamshell mode engages (given power + keyboard) and the GUI has a screen to render to. It genuinely solves both halves — which is why homelab people buy them in multi-packs. Costs: it occupies a port, it has to travel with the machine, and windows can land on a "screen" you can't see until you remote in.

Method 5: both halves in software (reminal — ours, disclosed)

reminal's closed-lid mode replaces the plug: it disables clamshell sleep and, the moment the Mac goes headless, creates a virtual display so GUI apps keep rendering — then streams every window and terminal, with input, into any browser (your phone included). Toggle off and everything reverts. Free and open source (AGPL); the virtual-display code is readable in the repo (vdisplay_darwin.go) if you want to check the claims.

Honest caveats: the closed-lid feature is macOS-only; and the virtual display rides the same private CGVirtualDisplay machinery DeskPad and BetterDisplay use — stable for years, but an OS update could change it (failure mode is "no display today", never a crash).

The fanless-Air caveat

MacBook Airs have no fan; they shed heat through the keyboard deck, and a closed lid reduces that. Bursty or light work is fine. Sustained heavy loads (long compiles, training runs) will thermal-throttle sooner than lid-open — consider standing the machine on its side, or a Pro with fans for sustained closed-lid duty.
